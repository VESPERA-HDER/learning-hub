四个流传很广但错误的说法

① 「YOLO11 用了 Transformer」——主干与颈部是纯卷积，只有末端 C2PSA 是注意力模块，且只作用在 20×20（400 个 token）上。
② 「YOLO11 是 anchor-based」——它是 anchor-free + DFL 回归。
③ 「YOLO11 端到端无需 NMS」——需要 NMS。免 NMS 是 YOLOv10 与 YOLO26 的特征。
④ 「YOLO11 有官方论文」——Ultralytics 明确表示不会为它发表正式论文，引用时应引软件仓库。

张量流追踪

选变体与输入分辨率，看 23 层网络的形状与参数量如何变化。这些数字由逐层推导引擎计算，并与 ultralytics 实际模型逐层对账（误差 ≤0.02%）。

怎么读这张表

· out 列是 [通道数, 高, 宽]，形状在 Concat 处翻倍、在 C3k2 处被压回——这就是 PAN 的呼吸节奏。
· 带 ★ 的层是结构改进的「热点位置」（第 13 层被复用两次、第 16/19/22 层是三个检测头的输入）。
· 对比 n 与 s：空间尺寸完全一样，只有通道数按 width 缩放。这也是为什么「同一张结构图在不同变体下标注不同」。

2.2 YOLOv8 → YOLO11 改了什么：四处改动逐条拆解

#改动v8 的做法YOLO11 的做法收益来源
1C2f → C3k2（主干与颈部全部替换） C2f：内部固定用 Bottleneck C3k2：内部可切换 Bottleneck / C3k / Bottleneck+PSA 低分辨率用重 block 换精度、高分辨率用轻 block 省算力。同一算力预算下配置更优
2新增 C2PSA（SPPF 之后） 主干末端只有 SPPF SPPF → C2PSA 在 20×20 的小特征图上做全局自注意力，代价低；半通道设计进一步压成本
3检测头分类分支 DWConv 化 cv3 = 两个标准 CBS(3×3) cv3 = DWConv(3×3) + Conv(1×1) 交替两次 高分辨率尺度上分类分支算力降约 8 倍，参数与延迟双降
4深度/宽度配置重新标定 各尺寸的 depth / width / max_channels 组合 重新标定（如 m/l/x 的 max_channels=512） 同等参数预算下通道分布更合理。这块贡献不可忽视
 ⚠️ 注意第 4 条：很多人以为提升只来自 C3k2 与 C2PSA，实际上缩放策略的重新标定贡献显著。做消融实验时务必把「结构改动」和「缩放改动」分开算。

conda create -n yolo11 python=3.10 -y

# ② 先装 PyTorch（去 pytorch.org 复制与你的 CUDA 版本匹配的命令）
#    CUDA 12.4 示例：
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu124

# ③ 再装 ultralytics
pip install -U ultralytics

# ④ 验证 GPU 是否可用
python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
新手最常踩的 4 个环境坑

① PyTorch 与 CUDA 版本不匹配 → torch.cuda.is_available() 返回 False。一定是先装对 PyTorch，再装 ultralytics。
② Windows 上路径含中文/空格 → 部分算子与缓存会报错。把工作目录（含数据集）放在纯英文路径下。
③ 显存不足 → 优先降 batch 或 imgsz，其次开 amp=True。
④ 报 No module named 'ultralytics' → 装的包和跑代码的解释器不是同一个。用 python -c "import sys; print(sys.executable)" 确认。

3.2 数据集准备：YOLO 格式与目录结构

my_dataset/
├── images/
│   ├── train/    # 训练图片，如 0001.jpg
│   └── val/      # 验证图片
└── labels/
    ├── train/    # 与图片同名的 .txt
    └── val/

# 每个 .txt 的每一行 = 一个目标：
#   class_id  x_center  y_center  width  height
#   全部为「相对图片宽高的归一化值」，范围 0~1
# 示例（第 0 类，中心在图中 (0.5,0.5)，占图 20%×30%）：
0 0.500000 0.500000 0.200000 0.300000
# data/my_dataset.yaml
path: /home/user/data/my_dataset     # 数据集根目录
train: images/train
val: images/val

nc: 3                                # = names 的长度
names:
  0: helmet
  1: person
  2: vest
数据准备阶段最容易毁掉整个项目的 5 个错误

① 图片与标签不同名（0001.jpg ↔ 0001.txt，后缀不同名相同）→ 该图被当成「无目标背景图」训练；
② 坐标没归一化（写了像素值）→ 框全部落到图外，loss 直接爆掉；
③ 类别 id 从 1 开始（YOLO 是 0-based）→ 最后一类永远学不到；
④ train / val 里有重复图片 → 验证指标虚高，线上崩盘；
⑤ 类目不均衡且被忽略 → 稀有类 mAP 极低，却被平均值掩盖。

3.3 训练前先做数据集体检

下面这个脚本只依赖标准库 + Pillow，训练前跑一遍能省下几小时的无用训练：

"""tools/check_dataset.py —— 检查图片/标签配对、坐标合法性、类别分布"""
from pathlib import Path
from collections import Counter
import yaml

root = Path("my_dataset")
cfg = yaml.safe_load(open("data/my_dataset.yaml", encoding="utf-8"))
names, nc = cfg["names"], len(cfg["names"])

for split in ("train", "val"):
    imgs = {p.stem for p in (root / "images" / split).glob("*")
            if p.suffix.lower() in {".jpg", ".png", ".jpeg", ".bmp"}}
    lbls = {p.stem for p in (root / "labels" / split).glob("*.txt")}
    print(f"[{split}] 图片 {len(imgs)} 张，标签 {len(lbls)} 个")
    print("  缺标签的图片:", sorted(imgs - lbls)[:5])
    print("  缺图片的标签:", sorted(lbls - imgs)[:5])

    cnt, bad = Counter(), []
    for f in (root / "labels" / split).glob("*.txt"):
        for ln, line in enumerate(f.read_text().splitlines(), 1):
            if not line.strip():
                continue
            parts = line.split()
            if len(parts) != 5:
                bad.append((f.name, ln, "字段数≠5")); continue
            c, x, y, w, h = int(parts[0]), *map(float, parts[1:])
            cnt[c] += 1
            if not (0 <= x <= 1 and 0 <= y <= 1 and 0 < w <= 1 and 0 < h <= 1):
                bad.append((f.name, ln, "坐标越界或未归一化"))
            if not 0 <= c < nc:
                bad.append((f.name, ln, f"类别 id {c} 超出 0~{nc-1}"))
    print("  类别分布:", {names[k]: v for k, v in sorted(cnt.items())})
    print("  异常标注:", len(bad), bad[:5])

3.4 三行代码跑通训练

from ultralytics import YOLO

# 1) 加载预训练权重（迁移学习，小数据集必做）
model = YOLO("yolo11s.pt")

# 2) 训练
results = model.train(
    data="data/my_dataset.yaml",
    epochs=150,
    imgsz=640,
    batch=16,              # 显存不够就降（或设 batch=-1 自动选）
    device=0,              # GPU 序号；CPU 用 device="cpu"
    workers=8,
    project="runs/helmet", # 实验根目录
    name="yolo11s_640",    # 本次实验名（结果存在 project/name）
    seed=0,
    pretrained=True,
    cache=False,           # 数据集小、内存大 → True 可显著加速
)

# 3) 验证
metrics = model.val()
print("mAP50-95:", metrics.box.map, "mAP50:", metrics.box.map50)
print("每类 mAP50-95:",
      dict(zip(metrics.names.values(), metrics.box.maps.round(3))))
# 等价 CLI 写法（服务器上很方便）

3.5 关键超参数逐个解释

参数默认它在控制什么什么时候改、怎么改
imgsz640输入分辨率，对小目标影响最大小目标多 → 768/960；嵌入式 → 416/320。FLOPs 与分辨率成平方关系
epochs100训练轮数小数据集（<2k 图）50~150 轮；大数据集 300+。配合 patience 早停
batch16批大小，影响 BN 统计与收敛稳定性显存允许下越大越稳；太小（<8）考虑换小模型
lr00.01初始学习率不收敛 → 降到 0.001；微调时通常降 10 倍
lrf0.01最终学习率 = lr0 × lrf（余弦退火）一般不动。后期震荡可适度调大
optimizerauto优化器，auto 按轮数与数据量自动选显式指定 SGD（稳）或 AdamW（小数据快收敛）
weight_decay0.0005权重衰减（防过拟合）过拟合 → 提 0.001；欠拟合 → 降 0.0001
box/cls/dfl7.5/0.5/1.5三项损失权重定位差 → 提 box；类别混淆 → 提 cls（谨慎，容易失衡）
mosaic1.0四图拼接增强的概率小目标检测必备；最后 10 轮自动关闭（close_mosaic）
mixup/copy_paste0.0混合增强 / 复制粘贴增强数据少时 mixup=0.1~0.2；稀有类用 copy_paste
degrees0.0旋转角度范围航拍/遥感 → 90 甚至 180；普通场景保持 0
fliplr/flipud0.5/0.0水平/垂直翻转概率有方向语义的任务（文字、左右手）要关掉 fliplr
hsv_h/s/v.015/.7/.4色调/饱和度/明度扰动光照变化大 → 加大 hsv_v；颜色是关键判别 → 减小
patience100多少轮无提升就早停小数据集设 20~30 省时间
ampTrue混合精度训练保持开启；出现 NaN loss 再关掉排查
close_mosaic10最后 N 轮关闭 mosaic默认即可。它是「指标突然跳升」的常见原因，别误判为异常
 超参默认值随版本可能微调，以 yolo cfg 或官方配置文档为准。
记忆口诀：改超参的顺序

先动数据（imgsz、增强），再动训练长度（epochs、patience），最后才动优化器与损失权重。新手常犯的错误是一上来就调 lr0 和损失权重，把本来能收敛的实验调崩。80% 的「模型效果不好」其实是数据问题，不是超参问题。

3.7 推理与导出

from ultralytics import YOLO

model = YOLO("runs/helmet/yolo11s_640/weights/best.pt")

# ---- 图片 / 目录 / 视频 / 摄像头 / 流 都支持 ----
results = model.predict(
    source="test_images",     # 也可以是 "video.mp4" / 0（摄像头）/ "rtsp://..."
    conf=0.25,                # 置信度阈值：低→召回高误检多
    iou=0.7,                  # NMS 的 IoU 阈值：低→框更少（抑制重叠）
    imgsz=640,
    max_det=300,              # 单图最大检测数（密集场景要调大）
    classes=None,             # 只检特定类，如 [0, 2]
    agnostic_nms=False,       # True = 跨类别抑制（类别易混时有用）
    half=True,                # GPU 上启用 FP16，提速
    save=True, stream=True,   # 视频/长目录 → stream=True 用生成器省内存
)

for r in results:
    for xyxy, conf, cls in zip(r.boxes.xyxy, r.boxes.conf, r.boxes.cls):
        x1, y1, x2, y2 = xyxy.tolist()
        print(f"{r.names[int(cls)]} {conf:.2f} [{x1:.0f},{y1:.0f},{x2:.0f},{y2:.0f}]")

# ---- 导出 ----
model.export(format="onnx",     opset=12, simplify=True, dynamic=False)
model.export(format="engine",   half=True, workspace=4)   # TensorRT（需在目标 GPU 上导出）
model.export(format="openvino", half=True)                # Intel CPU/核显
model.export(format="ncnn")                               # 移动端 / 部分国产 SoC
model.export(format="rknn",     name="rk3588")            # 瑞芯微 NPU
导出与部署的三条铁律

① 先验证精度再验证速度：每导出一个格式，都要用它跑一遍同样的验证集，确认 mAP 掉得可接受（ONNX/TRT FP16 通常掉 0~0.3，INT8 掉 0.5~2）。
② TensorRT engine 与硬件绑定：在 A 机器导出的 engine 换到 B 机器（GPU 型号/驱动/TensorRT 版本不同）会失效，必须在部署机上导出。
③ 务必融合 BN：Ultralytics 导出时自动 fuse，但你若手写推理代码，记得手动 fuse()，否则白丢 10%~20% 速度。

5.2 一句话经验

数据

先把数据看一遍（labels.jpg + 随机抽 30 张原图叠加标签），再动手训模型。80% 的效果问题源自数据。

分辨率

小目标的救命稻草是 imgsz 和切图，不是更大的模型。先把目标在输入里的像素尺寸算清楚。

对比

任何「提升」都要有同配置的 baseline 和至少 2~3 个随机种子。小于 0.3 mAP 的差距不要当结论。

部署

先跑通 predict，再跑 export，最后才做量化。每换一次格式就回归一次 mAP。

调试

出问题先做「降维测试」：imgsz=320 + 20 张图 + 10 个 epoch 能复现吗？能，就说明不是规模问题。

论文

把「工程技巧」和「结构创新」严格分开写。前者是你的 baseline 强度，后者才是你的贡献。

5.3 新手必问

Q1：YOLO11 到底有没有论文？我该怎么引用？

Ultralytics 官方明确没有为 YOLO11 发表正式论文。正确引用方式是引用软件仓库：
@software{yolo11_ultralytics, author={Glenn Jocher and Jing Qiu}, title={Ultralytics YOLO11}, version={11.0.0}, year={2024}, url={https://github.com/ultralytics/ultralytics}}
另外可引用第三方综述（如 arXiv:2501.13400）作为架构对比依据，但要注明是第三方分析。

Q2：n / s / m / l / x 我该选哪个？

按顺序问自己三个问题：① 硬件是什么？② 需要多少 FPS？③ 目标多大？经验法则：
· 首次跑通流程 → n；端侧/无人机 → n 或 s；
· 通用项目首选 → s 或 m（性价比拐点）；
· 精度优先、算力充足（服务器离线）→ l 或 x；
· 不要一上来就用 x，先用 s 把数据和流程验证完再升级。

Q3：mAP50 和 mAP50-95 差 18 个点正常吗？

完全正常。COCO 上典型模型 mAP50 约 70~75，mAP50-95 约 50~55，差 20 个点左右是常态。如果两者差距异常大（如 mAP50=95 而 mAP50-95=45），说明模型能检到但框不准，优先检查标注框是否贴合、是否有多余留白。

Q4：为什么我训出来的精度比论文低很多？

按可能性排查：① 数据集划分方式不同；② 训练轮数与增强参数不同；③ 没有从预训练权重出发；④ 你的数据集更难；⑤ 指标计算口径不同。论文数字只能在相同数据集与口径下比较。

Q5：需要多少张标注图才够？

经验锚点（迁移学习 + 少量类）：
· 100~300 张：能跑通 demo，精度勉强可用；
· 1000~3000 张：多数工业场景能达到可交付水平；
· 5000 张以上：可以开始考虑结构改进与刷指标。
关键变量是场景多样性（光照、角度、背景、遮挡）而不是绝对数量。1000 张高多样性 > 5000 张同质截图。

Q6：显存不够怎么办？

① 降 batch（8 → 4 → 2）；② 确认 amp=True；③ 降 imgsz（640 → 512）；④ 换小模型；⑤ cache=False；⑥ 用 batch=-1 让框架自动探测。

Q7：训练要多久？怎么估算？

粗略估算：单 epoch 时间 ≈ 数据量 / batch × 单步耗时。最可靠的方式是先用 20 张图跑 2 个 epoch 测出单步耗时，再乘出总时长。

Q8：能不能用 CPU 训练？

能，但慢 20~50 倍，「调试可以、正式训练不行」。折中方案是用云 GPU 按小时租，一张 3090/4090 每小时几块钱，训练 150 epoch 通常不到 20 元。这是研究生阶段性价比最高的选择。

Q9：损失在下降，但 mAP 一直很低，为什么？

典型原因是「损失下降 ≠ 指标上升」。逐项检查：① 验证集与训练集分布是否一致；② 是否过拟合；③ 标签分配是否异常（直接看 val_batch0_pred.jpg）；④ 指标是否被某几个难类拖累（看每类结果）。

Q10：如何做模型轻量化改进？

三条主流路线：
① 换主干（MobileNetV4 / EfficientViT）——收益明显但要注意三个尺度输出通道要与颈部对齐；
② 压缩颈部（减少 C3k2 重复次数、把高分辨率分支换成轻量卷积）——收益/成本比最高，因为颈部吃算力最多；
③ 量化 + 剪枝——不改结构即可部署提速。
建议从 ② 入手，改动可控、消融实验好写。

Q11：Transformer 一定比 CNN 好吗？

不一定。检测任务上 ViT/DETR 的优势主要在全局建模与端到端，代价是训练成本、显存与部署复杂度显著上升。在中小数据集上 CNN 通常仍更优（归纳偏置带来更强的数据效率）。YOLO11 的 C2PSA 已是「低成本混入注意力」的折中。若要做这个方向，务实做法是混合架构而不是全盘替换。

Q12：需要自己实现 NMS 吗？

不需要，Ultralytics 已内置且足够快。但必须理解两个参数：conf（置信度阈值）与 iou（NMS 的 IoU 阈值）。业务阈值要在「业务代价」下选，而不是在验证集上选最优 F1——安防场景漏报代价远高于误报，就应该把 conf 压低。
